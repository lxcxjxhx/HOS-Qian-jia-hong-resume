## PR 描述

## What this fixes

`_http_host` answered a URL's host with `urlsplit(url).hostname`. For the authority `http://[::1]@Example.COM/api` that answer depends on the Python version:

```
3.12  urlsplit(...).hostname  ->  'example.com'
3.13  urlsplit(...)           ->  ValueError: 'Example.COM' does not appear to be an IPv4 or IPv6 address
```

So the same URL was host `example.com` on 3.12 and `None` on 3.13. Since `_is_outbound_url` compares that answer against `_LOCAL_HTTP_HOSTS`, whether a URL in a scanned skill counted as local or outbound moved with the interpreter.

## Why the 3.12 answer is the wrong one

The test table that shipped with the surrounding refactor (#7950) already says what this shape should answer — `None` — because a bracketed literal where the userinfo belongs is a shape parsers disagree about: read one way the host is `example.com`, read another it is `::1`. It is the same reasoning the neighbouring cases encode (`http://user@[::1]:8080/api` → `::1`, `http://[::1/api` → `None`).

That is why `backend/tests/test_skillscan_native.py` fails on 3.12 today and passes on 3.13: the code and its own test disagree about a version-dependent parser behaviour.

## The change

Reject the ambiguous shape before `hostname` is read, so the answer no longer depends on the URL-parsing change. The URL keeps the treatment the other malformed authorities get: no host, and therefore outbound in `_is_outbound_url`, which is what that function's comment already says it does for malformed URLs.

The test table gains one more row, a bracketed literal with an IPv6 host and a port, so a fix that only special-cased the exact URL from the failure cannot pass:

```python
("http://[::1]@Example.COM/api", None),
("http://[2001:DB8::1]@example.com:8443/api", None),
```
