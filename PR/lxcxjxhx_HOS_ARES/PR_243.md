## 这是 PR #238 CI 失败的修复

PR #238 上 unit 与 integration **双双失败**，本地全绿。抓日志定位到根因：

```
docker: Error response from daemon: invalid option: read-only mode is not ...
FAILED test_sandbox_isolation.py::test_timeout_is_enforced_inside_the_container (125 != 124)
FAILED test_parallel_containers.py::test_each_task_runs_in_its_own_container ('error' != 'ok')
FAILED test_parity_items.py::test_only_e1_remains_unverified ({'E1','E5'} <= {'E1'})
```

GitHub 的 windows runner **有 docker CLI，但没有守护进程**。
`DockerRunner.available()` 当时只查二进制在不在 —— 于是被选中，接下来每条命令都 exit 125。

## 改了什么

| 改动 | 说明 |
|---|---|
| `available()` 探活 | 问一次 `docker info`（20s 超时），结果缓存。问不到就当不可用 |
| 降级链照走 | WSL podman → Job Object → BLOCKED —— 不再"选中一个注定失败的执行体" |
| `assume_alive=True` | **仅供验 argv 形状的用例**。它们不执行命令，判据是"加固项齐不齐" |

## 同一个教训的第三次换脸

| 批次 | 现象 | 修在哪 |
|---|---|---|
| B200 | docker CLI 在、守护进程不在 | **parity 探针** |
| B536 | 我在 `available()` 里又把「二进制在」当成「服务在」 | **执行体本身**（这次） |

这次修在源头：`available()` 一律探活，要跳过的用例显式声明。
**判据要放在最靠近事实的那一层** —— 放在上层再一层层兜，同一个坑就会换个地方再长出来。

## 一个副产品：CI 上 E1/E5 会如实记「未验」

CI 现在落到 Job Object，所以 `parity` 的 E1/E5 在 CI 上会是 `unverified` 而不是 `green`。
这正是 D3 要的形状：**没能验 ≠ 行为坏**。之前那条「E1/E5 必须 green」的用例
也已经改成按 detail 判断（#239 里改的），不会再逼着 CI 报假绿。
