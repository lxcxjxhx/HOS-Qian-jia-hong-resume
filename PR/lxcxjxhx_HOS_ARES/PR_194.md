## PR 描述

﻿## 判据

`platform --token` 的说明原来是“透传给每个资产”。企业现场每个资产一份凭据，一个 token 打通多台不只是“不准”——是把凭据送给了不该拿到它的机器。

## 改法（行为变更，带逃生门）

| 情形 | 行为 |
|---|---|
| 多资产 + `--token`（无确认） | **拒绝**，退出码 2，一个资产都不跑；提示两条出路 |
| 多资产 + `--token` + `--allow-shared-token` | 放行，报告写“**同一 token 注入 N 个资产**（已显式…）” |
| `--token-for 资产=token`（可重复） | 按资产注入；报告写“按资产注入 N 项（…）” |
| `--token` 与 `--token-for` 同时给 | 拒绝（搞不清哪个生效） |
| 单资产 + `--token` | 行为不变 |

## 实测

```
--token TOK（两资产）        → rc=2，调用 0 次
  stderr: 拒绝把同一个 token 发给 2 个资产（跨资产复用凭据）。
          按资产给：--token-for asset-1=<token> --token-for asset-2=<token>
          确实共用同一凭据再加 --allow-shared-token

--allow-shared-token         → tokens=['TOK','TOK']，报告“同一 token 注入 2 个资产”
--token-for asset-2=T2       → tokens=['','T2']，报告“按资产注入 1 项（asset-2）”
```

## 账本

H31 §2.3 新增：`--token-for` 的键随资产来源而变（`--profile` → 档里的 id；`--targets` → asset-N），报错里会列出可选键。

## 为什么敢改默认

风险不对称：静默透传的代价是凭据越界，拒绝的代价只是多打一行参数——而且给了显式逃生门 `--allow-shared-token`，不会把人卡死。

回滚：单提交 revert（回到透传；`--token-for` 一并消失）。
