## PR 描述

## 这一批是什么

给一份机器可读契约，自己解析出"有哪些面、每面属于哪个语义标签"——**但不回答"地址是什么"**。

## 最关键的一个决定：结构推断不能自行采纳

19 §3.1 第 5 行写着"仅有结构 → 不用"。如果照字面实现，客户契约没有 `x-veripen-tags` 时
**一个面都测不了**，A7 永远不可能达成。所以标签拆成两层：

| 层 | 谁能进 | 置信 |
|---|---|---|
| `adopted` | 契约显式标注 + **形状即声明**的四条 | 0.85 / 0.80 |
| `proposed` | 其余结构推断，等 profile selectors（= operator）确认 | 0.80 |

`SELF_EVIDENT` 只四条，理由写在代码里：
- `format: uri` ⟺ 会去取 URL → `url_fetch`
- 响应含 `access_token` ⟺ 发 token → `token_issue`
- `PATCH` + 自指段 → `profile_write`
- 分页参数 → `object_list`

**`api_read` 被彻底排除**：响应是 JSON 只说明它是 API，不说明能测什么。留着它每条 GET 都会灌满分母。

## 拒绝条件（启动即拒）

- 契约 `servers[].url` 的 host 不在 assets 解析集合 → **VP-1006**
- 标签用了字典外的词 → 直接失败（防标签漂移）
- operation 数超 `max_operations` → 失败

## 幂等

`opset_sha256` **不含文件哈希**（那标识"哪份文件"，不是"解析出什么"），且先按
`structural_key` 排序再序列化 —— 同一份契约换个书写顺序，内容寻址不变。这条有专门测试。
