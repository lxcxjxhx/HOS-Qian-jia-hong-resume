## 发现一个「看起来实现了、实际走不到」的能力

B521 声称实现了「一次给多个调用」（codex 式），`_plan_from_model` 里确实有：

```python
if isinstance(raw, (list, tuple)):
    # B521：允许模型一次给多个调用（codex 式并行读取）
```

**但那段代码从来没走到过。** 下层两道拦着：

1. **`_extract_payload` 把顶层数组当「多个对象」拒掉**：
   `json.loads` 得到 list → `isinstance(obj, Mapping)` 为假 → 落到 ③ 的"不许有第二个"分支；
2. `HttpChatClient.__call__` 末尾 **`return dict(parsed)`** 会把 list 转坏。

旧用例 `test_two_calls_rejected` 断言「多调用必须被拒」——**它守的正是不可达的那个分支**，
所以这个矛盾一直是绿的。

## 七种收场（这一批的核心）

| 收场层 | mode | 结果 |
|---|---|---|
| 计划层降级 | `prose`（说人话） | 退回 rules，reason 带出模型原文 |
| 计划层降级 | `empty` / `null` | 「content 是空的」 |
| 计划层降级 | `bad_schema`（未知工具） | 「不合规的调用」 |
| **执行层拒绝** | `extra_field` | `bogus: Extra input` |
| **执行层拒绝** | `missing_field` | `rel: Field required` |
| **正常接受** | `two_calls`（数组） | 2 个 Step 依次执行 |

最后一条是**必须接受**的——把它和前面放在一套里，证明判据不是"一律拒绝"。

字段错误故意不在计划层降级：交给工具面的 pydantic（`extra="forbid"`），
好处是**错误落到具体字段**上，而不是笼统的「模型给了不合规的调用」。
