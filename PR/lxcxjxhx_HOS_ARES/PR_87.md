## 背景

`B30` 在真实目标（Google Firing Range）上召回 **0.33**，`H09 §4` 记为开放问题 #3，归因写"属契约解析，未排批"。

但**推断器早就写好了**：`parser._structural_tags` 能从方法 / 参数形态 / 响应内容类型推断 10 类语义标签，结果进 `Operation.proposed`（`source=structural`，`conf 0.80`），等 operator 用 `confirm` 确认（`19 §3.1` 第 5 行：仅有结构不直接采纳）。

缺的是：**`plan()` 的 `confirm` 参数从来没有调用方传过**。于是 `proposed` 永远躺着，无标签的 operation 一律记 `no_tags` 跳过。

这与 `B62`（`injectable()` 零调用）、`B63`（`with_knowledge()` 只在测试里）是同一类欠账：**模块在、接线零**。

## 改动

| 项 | 内容 |

| `cmd_run` | `--confirm-structural`（全采纳）/ `--confirm-tags`（指定标签） |
| `cmd_platform --profile` | 用档的 `selectors` 作为 confirm —— 那是 operator 在客户档里写的"我确认这些面存在" |

## 一条不能松的纪律

采纳后 `source` 保持 `structural`、`conf 0.80` < 契约显式 `0.95`：

```
标签：结构推断 3 类（object_read, param_injectable, url_fetch）—— 置信 0.80，低于契约显式 0.95
```

`/api/items/{id}` 看起来像 `object_read`，但可能只是返回列表。**猜错时要能一眼看出这条面是靠猜的**，不许抹成 contract。
