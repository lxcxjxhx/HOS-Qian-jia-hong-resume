## PR 描述

## 背景

干净 clone 复验时，`check-plan` 报 **MANIFEST 过期：H00-总纲与四波排期.md**。

这是同一笔债的**第三次复发**：

- B60 修的是工作区（`git rm --cached -r .` + `reset --hard` 重写为 LF）
- B65 修的是"再重生成一次"
- 两次都只解决了"这一次恰好对了"，没解决"为什么会对不上"

根因：`check-plan.cjs` 与 `_gen_manifest.cjs` 直接对**原始字节**算 sha。
Windows 上手动编辑 md 会产生 CRLF，`--write` 把 CRLF hash 冻进 MANIFEST；
而 `.gitattributes` 声明 `eol=lf`，`git add` 存的是 LF blob，
**任何 LF 环境都会判过期**。

## 修法（修在脚本层）

| 文件 | 改动 |
|---|---|
| `plan-hos-ares/check-plan.cjs` | 读文件后 `normalize(CRLF→LF)` 再算 sha / bytes / lines |
| `plan-veripen/_gen_manifest.cjs` | 同一条纪律 |
| `plan-veripen/_verify-manifest.cjs` | 校验端必须与生成端一致，否则 Windows 上每行都 MISMATCH |

两个 MANIFEST 重生成；`PLANS.md` 的 kernel / program sha16 同步。

## 验收：证明"真的免疫"

关键不是"这次绿了"，而是**把 CRLF 塞回去仍然绿**：

```
1. plan-hos-ares/H15-成片与一键演示.md  3057B(LF) → 3124B(CRLF)
2. node plan-hos-ares/check-plan.cjs
   → structure OK（MANIFEST 18 files）        ← 修复前必报"过期"
3. 转回 LF
```

干净 clone 的 `check-plan` 也回到 OK。

```
cd plan-veripen && node _verify-manifest.cjs  → OK: 54 files verified
node plan-hos-ares/check-plan.cjs              → structure OK
node scripts/plan/check-plans.cjs              → governance OK
ledger-check                                   → batches=116 problems=0
pytest tests/unit                              → 全绿
```

## 为什么值得单独一批

这类"内容寻址 vs 行尾"的债不会被功能测试抓到（单测、parity、doctor 全绿），
只有**换一台机器/换一个 clone** 才暴露。第三次复发说明前两次修的是症状。

修完之后，行尾从此不影响内容寻址——这才是"根治"。
