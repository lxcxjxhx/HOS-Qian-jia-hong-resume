## Summary

`ExperimentResults.compare_with_baseline` reads the baseline JSON with a bare `open(...)`, so it decodes with `locale.getpreferredencoding(False)` — cp1252 or cp936 on Windows. A baseline written as UTF-8 therefore comes back as different strings, and a result whose identifier contains non-ASCII text stops matching itself:

```text
with the fix     {"unchanged": 1, "new_tests": 0, "missing_tests": 0}
without the fix  {"unchanged": 0, "new_tests": 1, "missing_tests": 1}
```

That is the symptom the issue describes: nothing changed, but the same test is reported as both new and missing. The three writers were only safe by accident, because `json.dump` defaults to `ensure_ascii=True`; they now state the encoding instead of depending on that, so a later `ensure_ascii=False` for readability cannot corrupt the file.

Four calls in `lib/crewai/src/crewai/experimental/evaluation/experiment/result.py` gain `encoding="utf-8"`: the reader in `compare_with_baseline` and the three writers (`to_json` and the two baseline writes).

Not touched: `telemetry/tracing/last_run.py` opens a lock file, but the handle only goes to `fcntl.flock` and is never written to.

## Verification
