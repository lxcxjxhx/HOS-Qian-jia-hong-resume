## PR 描述

## Purpose of the pull request

Fix #18015. `$[yyyy-MM-dd-1]` subtracted one hour too much when the range crossed a daylight
saving time transition, which could move the result a whole day early.

Reproduction in `America/Los_Angeles` (the reporter's environment):

```
base           2026-03-09 00:10 PDT
yyyy-MM-dd-1   2026-03-07 23:10 PST     <- expected 2026-03-08 00:10
```

2026-03-08 is a 23-hour day (02:00 -> 03:00), so subtracting a fixed 1440 minutes lands at 23:10 of
the *previous* day instead of 00:10 of the target day.

## Brief change log

`calcMinutes(String)` converts a day count into minutes via `60*24*(n)`, and the result is applied
through `DateUtils.add(date, Calendar.MINUTE, n)`, i.e. as an absolute duration. A day is not always
24 hours, so the conversion is only correct on days without a DST transition.

A bare operand is a **day** count — `$[yyyyMMdd+1400]` is +1400 days, which
`TimePlaceholderUtilsTest#timePlaceHolderWithFourDigitDayOffset` pins. An operand containing a
division is a **minute** expression — `-1000/24/60` means -1000 minutes, pinned by
`ParameterUtilsTest`. Both meanings must be preserved, so one private helper now branches on the
presence of `/`:

```java
private static Date addOffset(Date date, String offsetExpression, int sign) {
  if (offsetExpression.indexOf(DIVISION_CHAR) == -1) {
    return addCalendarDays(date, sign * calculate(offsetExpression)); // whole days -> calendar days
  }
  return addMinutes(date, sign * calcMinutes(offsetExpression));      // contains '/' -> minutes, unchanged
}
```

- Call sites: the `+` and `-` branches of `calcMinutes(String, Date)`, and `calcFormatOffset`.
- `calcMinutes(String)` itself is untouched, so the division path keeps its exact previous behaviour.
- No new dependency, no signature change, no public API change.

### Calendar-day arithmetic runs in the request timezone

`addCalendarDays` shifts the local date in the timezone the placeholder is parsed and formatted in
(the request timezone held in `ThreadLocalContext`), not the JVM default timezone:

```java
private static Date addCalendarDays(Date date, int amount) {
  String timezone = ThreadLocalContext.getTimezone();
  ZoneId zoneId = StringUtils.isNotEmpty(timezone) ? ZoneId.of(timezone) : ZoneId.systemDefault();
  return Date.from(date.toInstant().atZone(zoneId).plusDays(amount).toInstant());
}
```

`DateUtils.addDays` uses `Calendar.getInstance()` and therefore the JVM default timezone. When the
JVM runs in UTC and the request timezone is `America/Los_Angeles` (a supported, common deployment),
computing the offset in UTC and formatting the result in Los Angeles reintroduces the same one-hour
shift the issue reports. Shifting the local date in the request timezone keeps the arithmetic and the
formatting in the same zone; the system zone is used only when no request timezone is set.

The shift is applied to a `ZonedDateTime`, not a `LocalDateTime`. Converting the instant to a
`LocalDateTime` discards its UTC offset, and an ambiguous local time — the hour repeated when DST
ends — is then always resolved to the *earlier* occurrence, so even a zero-day offset moved the
instant by one hour. Keeping the value zoned makes `plusDays` retain the original offset whenever the
shifted local time is ambiguous.

## Known limitation (measured, not theoretical)

An offset written with a division keeps the legacy minute semantics, so the *same* number of days
expressed with `/` still drifts by an hour across a DST boundary:

```
base              = 2026-03-09 00:10 PDT
yyyy-MM-dd-7      = 2026-03-02 00:10     <- correct
yyyy-MM-dd-7/1    = 2026-03-01 23:10     <- still 1 hour early
yyyy-MM-dd-168/24 = 2026-03-01 23:10     <- same
```

This is deliberate: `$[HHmmss+2/24]` (+2 hours) and `$[HHmmss+3/24/60]` (+3 minutes) are pinned to
minute semantics by `ParameterUtilsTest`, so an operand containing `/` cannot be reinterpreted as
whole days. Telling `7/1` (7 days) apart from `2/24` (2 hours) would need a heuristic on whether the
result divides 1440 — the approach that got the two previous attempts at this issue rejected.
Making division operands fully DST-safe needs an explicit unit suffix, which is a separate API
design question.

Would you prefer this PR to (a) keep the current `/` boundary as documented above, or (b) also
introduce an explicit unit syntax? I am happy to do (b) as a follow-up.
