## PR 描述

`sandbox_edit_file` 在 `oldContent` 未匹配时仍返回编辑成功，导致 Agent 误以为修改已生效（#8326）。本次让文件系统返回逐条编辑状态，并统一不同 provider 的停止策略与模型反馈。

## 实现

- `replaceContent` 返回与输入顺序一致的 `ContentReplaceResult[]`，结果路径统一为 provider 规范化后的路径。结果使用四种明确状态：`replaced`（携带实际替换次数）、`unmatched`（明确零匹配）、`unknown`（请求完成但缺少计数，修改可能已生效）、`skipped`（未执行）。
- OpenSandbox 使用 SDK 1.2.0 已有的 `replaceContentsDetailed`。保留同文件串行分批，通过原始索引回填每条结果；批次内按路径关联响应，不跨批次累计计数，也不依赖响应顺序。结果默认初始化为 `skipped`，执行后逐条覆盖，停止时不再遍历剩余批次构造伪异常。
- OpenSandbox 与 command polyfill 均在明确未命中后停止发送后续请求，后续条目保持 `skipped`。当前已发送请求里的其他编辑可能已经生效。`unknown` 不触发自动重试，也不会被误判为未命中。
- command polyfill 复用业务输入类型和同一次文本拆分，返回实际匹配次数；未命中时不写文件，保留已有 UTF-8、BOM、权限与临时文件原子替换行为。
- 全部成功时保留原成功文案；其他情况按输入条目序号反馈每条状态，最后统一提示读取文件确认后再重试。未命中、未知和跳过都作为普通 `tool response` 返回；真实参数、I/O 和传输异常继续沿现有 Agent 异常处理链路回填工具响应，内部事件可记录 `errorMessage`。
- 新结果类型直接从定义文件导入，未扩展 barrel 转导；新增关键步骤说明使用中文注释。

例如，同一文件依次执行 `old → new`、`missing → unused`、`new → final`，两种 provider 均返回 `replaced / unmatched / skipped`，最终内容为 `new`。后端已执行但未返回计数的条目为 `unknown`，与未发送的 `skipped` 分开反馈。
