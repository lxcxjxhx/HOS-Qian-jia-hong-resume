## PR 描述

## What

The eval toolchain reads and writes its text artifacts (suite manifest, conversation JSON, debug logs, traces, results) without an explicit encoding, so it uses the platform default: UTF-8 on Linux/macOS, the ANSI code page on Windows (GBK on a zh-CN machine, cp1252 on en-US).

The sharpest consequence is that **a manifest cannot be loaded at all on Windows** if it contains any non-ASCII text — a scenario title in another language, an em dash in a description, a bot name with an accent:

```python
from pipecat.evals.suite import EvalManifest

manifest = Path(tmp) / "manifest.yaml"
manifest.write_text("name: café — 测试\nbots_dir: bots\n", encoding="utf-8")   # valid UTF-8, as shipped/written on POSIX

EvalManifest.load(manifest)
# UnicodeDecodeError: 'gbk' codec can't decode byte 0x94 in position 14
```

`EvalManifest.load` does `yaml.safe_load(path.read_text())`, and `read_text()` with no argument decodes with `locale.getencoding()`.

The writes have the mirror problem: artifacts produced by a run on Windows are not UTF-8 either, so they cannot be read back on POSIX, by a container, or by the tooling that consumes `results.json` — and a character outside the ANSI code page raises `UnicodeEncodeError` after the run has already happened.

## Change

`encoding="utf-8"` on the 14 text-mode sites in the eval toolchain:

| file | sites |
|---|---|
| `src/pipecat/evals/suite.py` | 8 (manifest read, conversation/body/config/trace/log writes, results read) |
| `src/pipecat/cli/commands/eval.py` | 4 (eval log, conversation JSON, traceback log, conversation read for judging) |
| `src/pipecat/evals/conversation_observer.py` | 1 (`call.conversation.json`) |
| `src/pipecat/evals/simulation_judge.py` | 1 (`run.conversation.json` read) |

Binary opens are deliberately untouched: `files.log.open("wb")`, `files.harness_log.open("wb")`, `wave.open(..., "wb")` and `Image.open` carry no encoding.

No behaviour change on POSIX, where UTF-8 is already the default.
