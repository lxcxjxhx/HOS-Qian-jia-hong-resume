## PR 描述

Three text-mode `open()` calls still rely on the platform default encoding, after the eval toolchain was made explicit in #6606 / #6608 / #6612.

| file | site | consequence today |
|---|---|---|
| `src/pipecat/evals/suite.py` | `results_path.open("a")` in `_append_result` | **real** — writes `results.jsonl` with the ANSI code page on Windows, so a run that logs a non-ASCII string produces a file a POSIX reader or a container cannot decode |
| `src/pipecat/services/google/stt.py` | `open(credentials_path)` in the Google STT `__init__` | **real** — a service-account JSON that is valid UTF-8 but contains any non-ASCII byte (a name, a comment, a non-Latin project id) raises `UnicodeDecodeError` on a Windows box |
| `src/pipecat/cli/commands/eval.py` | `output.open("w")` in `_judge_all` | latent — the lines are `json.dumps(...)` with the default `ensure_ascii=True`, so the bytes happen to be ASCII-only; the encoding is correct by accident of that default, not by declaration |

**Deliberately unchanged:** `src/pipecat/utils/…/init.py` and anything else that writes through a child process, where the subprocess applies its own default and pinning a parent-side encoding would not reach it. No binary opens are touched.

No behaviour change on POSIX, where UTF-8 is already the default.

**Verification:** `ruff check` / `ruff format --check` clean on the three files; the diff is three lines.
