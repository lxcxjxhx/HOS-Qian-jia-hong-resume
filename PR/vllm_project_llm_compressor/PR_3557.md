## PR 描述

## What this fixes

`MoEConfig.from_config()` falls back to `softmax` when a config declares none of `scoring_func` / `score_func` / `moe_router_activation_func`, but for three `model_type`s the transformer module hard-codes sigmoid and the published configs say nothing:

| `model_type` | router in transformers 5.23.0 |
|---|---|
| `glm4_moe` | `Glm4MoeTopkRouter` → `.sigmoid()` |
| `glm4v_moe_text` | `Glm4vMoeTextTopkRouter` → `.sigmoid()` |
| `glm4_moe_lite` | `Glm4MoeLiteTopkRouter` → `.sigmoid()` |

RAZOR renormalizes these scores for its damage estimate and for the promotion ranking, so on those checkpoints it works with softmax weights where the router uses sigmoid ones (all four configs set `norm_topk_prob: true`).

The analysis and the file/line pointers are from #3556; I only verified them against the installed transformers source and turned them into a patch.

## How it is fixed

The fallback default becomes model-type aware:

```python
DEFAULT_SCORE_FUNCTION_BY_MODEL_TYPE = {
    "glm4_moe": "sigmoid",
    "glm4v_moe_text": "sigmoid",
    "glm4_moe_lite": "sigmoid",
}
```

```python
            score_function=_getattr_fallbacks(
                config,
                ["scoring_func", "score_func", "moe_router_activation_func"],
                DEFAULT_SCORE_FUNCTION_BY_MODEL_TYPE.get(
                    getattr(config, "model_type", None), "softmax"
                ),
                warn_on_default=True,
            ),
```

This is deliberately not written as an after-the-fact `self.score_function = "sigmoid"` override (the shape used for `qwen3_5_moe_text` above it), for two reasons:

1. A `scoring_func` the config **does** declare still wins, because this is only the fallback — no extra `hasattr` guard needed.
2. The warning stays truthful. With an override the log still prints `Defaulting to softmax` for a model that then ends up on sigmoid, which is part of why this looked like a config problem.
